# Working Agreements

用户在多轮协作中反复表达过的工作方式偏好。
**这些不是礼节问题，是返工与不返工的差别。**

---

## 语言

**用中文回复。** 代码注释也用中文（现有代码库就是这个风格）。
提交信息用中文，遵循仓库既有格式：标题一行 + 空行 + 分段正文说明「改了什么、为什么」。

---

## 审计先于实施

改动现有真实业务数据结构之前，**先输出审计**，确认后再动手：

```
现有数据能支撑什么
不能支撑什么
需要哪些改动
风险在哪
```

这个模式从祷告室改造起就固定下来了（SEC-1 / Phase 2 / Phase 5 / P1-2 都先审计）。
用户明确说过「不修改现有真实业务数据结构之前先审计」。

大阶段完成后写一份阶段报告到 `docs/`（如 `PRAYER_ROOM_PHASE5_REPORT.md`）。

---

## 证据标准 —— 这是最硬的一条

> **不要只写「测试通过」。**

用户反复要求的：

```
不能只靠单元测试
不能用 mock PASS 宣称生产能力已验证
必须给实际跑出来的数字，不引用文档里的旧数字
失败就说失败并贴输出；跳过了某步就说跳过
```

具体标准：

| 要证明的 | 可接受的证据 |
|---|---|
| 权限 / 并发 / 持久化 / 跨房隔离 | 真 backend + 真 SQLite + 真 HTTP + 真 JWT |
| UI 不白屏、假象不复活 | 真浏览器（Chrome + puppeteer-core） |
| 「不是内存状态」 | **真的 kill 掉 backend 再重启**，验证状态还在 |
| 「失败时不显示假数据」 | **真的 kill 掉 backend**，看 UI 说什么 |
| 双向语音互听 | 两台真机 + 真实人耳（做不到就写 BLOCKED） |

**报告必须明确写出 `FAIL 数：X`。** 不是 0 就不能包装成完成。

出现 FAIL 时要区分**真实缺陷**与**验证脚本自身的误报**，并各自说明。
（P1-2 出过 6 个 FAIL：4 个是守卫顺序的真实缺陷，2 个是我自己写的粗糙正则误报。）

---

## 不做「看起来很真实」的东西

这是整个项目的第一原则，用户原话：

> **没有真实数据，就不做看起来很真实的 UI。**

推论：

- 未知不是零。算不出来就写「未记录」，不写 0
- 拿不到的指标**字段都不返回**，不是返回 0 —— 客户端连渲染成 0 的机会都不给
- 房里只有一个人就显示「1 人在线」，不补头像凑好看
- 说明文案不得承诺没实现的功能

---

## 范围纪律

用户会明确划定「本轮不做什么」，那是硬边界：

```
禁止顺手重构已经验收通过的核心模块
禁止重新实现已经 DONE 的阶段
禁止把已否定的 Legacy 方案做回来
禁止未经允许扩大范围
```

用户说过「不要重新推翻当前整体视觉风格」——
暖米白 + AMAS 深蓝 + 古金是定下来的方向，不要另起炉灶。

祷告室的浅色主题色值集中在 `components/VoiceRoom/prayerTheme.ts`，
**硬编码色值视为回归**。

---

## 破坏性操作

用户希望**由人按下回车**：

```
force push · 历史重写 · 删远端分支 · rm -rf 用户数据 · 清空生产数据库
```

Claude Code 的权限门禁也会拦。正确做法：写好脚本 + 说清风险 + 提供回滚方式，
交给用户执行。**不要换个 shell 去绕过门禁。**

删除任何东西之前先看一眼目标内容，并说明「删了会失去什么」。
（曾经在删一个「旧备份」目录前发现它有 42 个 main 里没有的提交。）

---

## 承认错误的方式

用户能接受出错，不能接受粉饰。发现自己之前说错了：

- 直接改正，说明错在哪、正确结论是什么
- **文档里的错误结论要留痕**，标 `SUPERSEDED` 或写「勘误」段落，不要静默删掉
- 不要反复道歉，不要长篇自责，改完继续

本项目已经发生过的勘误（都保留在文档里）：

| 错误结论 | 更正 |
|---|---|
| 「Phase 1 已验证 mock 场景零幽灵成员」 | 断言根本没生效（`import.meta` 别名陷阱），报告作废重做 |
| 「内置房间没有 manager，谁也创建不了祷告会」 | 错。`requireRoomManager` = host **或** moderator，机制早就有 |
| 「376344d 未共享」 | 依据是过期的本地缓存 ref，当时无法访问远端复核 —— 结论碰巧对，但推理过程不成立 |

---

## 沟通风格

- 先给结论，再给依据
- 表格优于长段落
- 不确定就说不确定，不要用模糊措辞掩盖
- 不要为了显得有进展而夸大完成度
- 遇到真正需要用户拍板的分叉（会导致不同的工作），**问**；
  常规判断自己做，说明一句即可
