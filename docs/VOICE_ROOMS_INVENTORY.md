# 其它四个语音房间｜现状盘点

**本轮只盘点，不改代码。**

范围：赞美室 / 读经室 / 讲道室 / 交通室。祷告室已在 Phase 1–5 重做完毕，
这里只作为对照基准。

---

## 一、两套完全不同的实现

祷告室和其它四间根本不是同一套东西：

| | 祷告室 | 其它四间 |
|---|---|---|
| 组件 | `PrayerRoomPanel.tsx`（1011 行） | `VoiceRoomOverlay.tsx`（1624 行） |
| 视觉 | 暖米白浅色，`prayerTheme.ts` 单一色源 | 深色渐变，色值散落在 JSX 里 |
| 数据 | 后端 SQLite，12 个 REST 端点 | **几乎全部是本地 `useState` / `localStorage`** |
| 成员 | `room_members` + `room_presence`，真实 | 只有「我」一个人，写死 |
| 实时 | SSE 失效通知 + 轮询降频 | 无 |
| 权限 | host / moderator / member 三级，服务端判定 | 全部客户端自判 |
| 结束沉淀 | 纪要 + 历次历史 | 无 |

**进入房间时其它四间不调用后端任何接口。**
`enterRoom()`（`CommunityView.tsx:628`）只是 `setTimeout(500)` 后设本地 state。
`joinRoom()` 全项目只有 `PrayerRoomPanel.tsx:564` 一处调用。
所以这四间房里：没有 membership、没有 presence、没有心跳、没有任何服务端记录。

## 二、逐间盘点

### 2.1 读经室 —— **底子最好的一间**

**真实资产：**

`public/scripture/cuv.json` 实测 **66 卷 / 31,103 节**，完整和合本，3.3 MB，
离线可用，无需网络也无需 AI。`services/scriptureService.ts` 懒加载 + 模块级缓存，
有 5 项单元测试。这是四间房里唯一一份货真价实的内容资产。

选经文（`BIBLE_STRUCTURE` 全 66 卷章数正确）、切章节、字号调节 —— 都是真的。

**问题：**

| 项 | 现状 |
|---|---|
| 「经文会自动同步给房间内所有参与者」 | **假的**。`currentBibleChapter` 是纯本地 `useState`，从不发给任何人。这句话写在 `constants.ts` 的房间说明里，用户看得见 |
| `INITIAL_BIBLE_DATA` | 硬编码创世记 1 章、诗篇 23 篇各 5–6 节，作为首屏默认值。cuv.json 里有全本，这份重复数据没有存在必要 |
| 阅读进度 | 不保存。退出即丢 |

### 2.2 讲道室 —— **有一个真功能**

**真实资产：**

`SermonRecorder`（`services/recordingService.ts`）是真的：
`getUserMedia` + `MediaRecorder`，每秒切块，上传到 `POST /api/recordings`，
后端落盘 + 元数据入库。分享到校友圈也是通的。

讲章大纲存 `localStorage`，说明里写明「仅自己可见」—— **诚实**，没有承诺同步。

**问题：**

| 项 | 现状 |
|---|---|
| 录的是什么 | 只录**本机麦克风**。多人房间里录不到别人。目前单人自录语义成立，真实语音上线后需要重新界定 |
| 与 Voice 的边界 | Phase 4 §25 禁止录制祷告 / 云端录音 / 自动转写。讲道录音是讲员本人主动发起的独立功能，不冲突，但**真实语音接入后必须重新划线**，不能顺势变成「录整个房间」 |
| 听众端 | 除了本地回应动画，什么也没有 |

### 2.3 赞美室 —— **最严重的一间**

**没有任何音频播放代码。**

`isPlaying` 默认 `true`，界面显示跳动的均衡器动画、歌名「这一生最美的祝福 ·
赞美之泉」、暂停按钮。全项目搜不到 `<audio>`、`new Audio()`、任何播放器。
`PRAISE_SONGS` 是 3 条只有标题/歌手/时长的硬编码元数据，**没有音频文件**。

也就是说：用户进赞美室，看到「正在播放」，点暂停有反应，**从头到尾一片安静**。

房间说明还写着「所有人都可以跟着音乐一起敬拜」—— 既没有音乐，也没有同步。

| 项 | 现状 |
|---|---|
| 播放 | ✗ 不存在 |
| 歌单 | ✗ 3 首硬编码元数据，无音频 |
| 点歌同步 | ✗ 纯本地 |
| 版权 | 未处理。真要放诗歌，授权是先决条件 |

### 2.4 交通室 —— **一间空房**

全文件搜 `fellowship`，**只有一处命中**：背景渐变色。

没有任何专属功能。房间说明承诺三件事：

- 「自由分享生活见证和感恩事项」 → 没有任何分享机制
- 「举手即可申请上麦发言」 → **假的**，见 §3.2
- 「彼此鼓励，互相代祷」 → 没有代祷机制（祷告室的代祷墙没有接进来）

## 三、四间房共有的问题

### 3.1 成员列表只有「我」一个人

```ts
const [participants, setParticipants] = useState<Participant[]>(() => ([
    { id: 'me', name: '我', ... },
]));
```

`VITE_VOICE_TRANSPORT` 现在是 `none`（Phase 1 的安全默认），
`NoopTransport` 不产出任何远端成员 —— **这是好事，没有幽灵成员**。
但结果是：不管多少人同时进同一间房，每个人看到的都只有自己。

界面上却仍有「左五人 / 右五人」的舞台布局、host/admin 角标、
静音图标、说话光环 —— 一整套为多人设计的 UI，服务于一个恒为 1 的列表。

### 3.2 举手上麦是一段脚本

```ts
const handleRaiseHand = () => {
    showToast('已举手申请发言任务...');
    safeSetTimeout(() => {
        setParticipants(prev => prev.map(p => p.id === 'me' ? { ...p, role: 'speaker' } : p));
        showToast('主持人邀请您上麦');     // ← 没有主持人，没有人邀请
        setIsMicOn(true);
    }, 1000);
};
```

没有请求、没有审批、没有主持人。等 1 秒然后自己把自己提成 speaker，
再弹一句「主持人邀请您上麦」。**这是四间房里最像真的一处假象。**

### 3.3 礼物、快捷回应、聊天 —— 全是本地独角戏

`handleSendGift` / `triggerReaction` / `handleQuickResponse` 只改本地
`roomChats` 与 `reactions`。`initialChats` 上层传的是 `[]`（**没有伪造聊天记录，这点是干净的**），
但你送的礼物、发的「阿们」，房间里其他人永远看不到。

### 3.4 房间密码：后端已有，客户端仍有回落

`handleConfirmPassword` 优先走后端 `validateRoomPassword`（timing-safe + 服务端哈希），
但在 `not-registered / network` 时**回落到客户端明文比对** `inputPassword === pendingRoom.password`，
而该密码存在 `localStorage` 里。

代码注释里早就写明了这点。离线可用是有意的取舍，但**不能对外宣称「私密房间」**。

### 3.5 一整块死代码

`VoiceRoomOverlay.tsx:1259–1293`：`isBibleRoom` 分支内部又判断 `isPrayerRoom`，
恒为 `false`。里面是旧版深色「祷告墙」，连同 `prayerWallContent` 状态、
`DEFAULT_PRAYER_WALL` 默认文案、以及每 500ms 写一次的 localStorage 持久化，
**全部不可达**。祷告室重做后遗留的。

### 3.6 AI 牧者只在祷告室自动连接

```ts
if (currentType === 'prayer' && !isAiConnected && !isAiLoading) connectToGemini();
```

其它三间要手动触发（`VoiceRoomOverlay.tsx:453`）。
目前 `GEMINI_API_KEY` 未配置，握手必然失败 —— Phase 5 验证时抓到的
4 条 WebSocket 报错就是它。

## 四、后端现有能力（重要）

**这些表和端点本来就是按 `room_id` 设计的，不是祷告室专属：**

| 表 | 用途 | 能否直接服务其它房间 |
|---|---|---|
| `rooms` | 房间 + 密码哈希 | ✅ 五间都已 seed |
| `room_members` | 成员 + moderator | ✅ 完全通用 |
| `room_presence` | 在线心跳 | ✅ 完全通用 |
| `room_prayer_topics` | 房间主题列表 | ⚠️ 表名带 prayer，结构通用 |
| `prayer_shares` + `prayer_intercessions` | 分享 + 登记 + 匿名 + 治理 | ⚠️ 同上 |
| `prayer_sessions` + `_items` + `_events` | 有序议程 + 当前项 + 事件日志 | ⚠️ 同上，机制完全通用 |
| `room_realtime_events` | SSE 失效通知 | ✅ 完全通用 |
| `recordings` | 讲道录音 | ✅ 已在用 |

也就是说：**读经进度、讲道大纲、交通分享，需要的服务端机制基本都已经存在**，
差的是接线，不是从零建表。

`prayer_sessions` 尤其值得注意：它就是一个「有序条目 + 当前进行到哪一项 +
谁在带领 + 乐观并发 + 事件日志」的通用状态机。
读经计划（今天读哪几章）、讲道大纲（讲到第几点）用的是同一套东西。

## 六、按「先别骗人，再谈做功能」排出的优先级

沿用这一路的规矩：**没有真实数据，就不做看起来很真实的 UI。**

### P0 —— 假象，应当先拆掉（不需要新功能）

1. 赞美室「正在播放」+ 均衡器动画 —— 没有音频就不要显示播放态
2. 举手上麦的 1 秒脚本 + 「主持人邀请您上麦」
3. 读经室说明里「经文会自动同步给房间内所有参与者」
4. 交通室说明里三条都没有实现的承诺
5. 1259–1293 的死代码 + `prayerWallContent` 全套

拆掉之后这几间房会显得很空 —— **那才是它们真实的样子**。

### P1 —— 用已有后端能力，最小成本接真

6. 四间房复用 `joinRoom` / `heartbeat` / `presence`，让成员列表变成真的
7. 读经室：阅读位置存服务端（复用 `prayer_sessions` 的当前项机制），
   让「同步」从假话变成真话
8. 交通室：接祷告室已有的分享墙（含匿名、举报、隐藏、软删除治理链）

### P2 —— 需要新资产或新决策

9. 赞美室音频：需要**版权授权**和音频托管方案 —— 这是产品/法务决策，不是技术任务
10. 把 `room_prayer_topics` / `prayer_shares` 等表名与路径泛化为 room-generic
    （纯重命名迁移，收益是概念清晰，风险是动到已上线的真实数据）
