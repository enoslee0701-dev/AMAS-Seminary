## 0. 一句话结论

**能做，但这不是一次「换皮」。**

设计稿的副标题「同心合意，为国度祷告。」与现有代码 `THEME_CONFIGS.prayer.desc` **一字不差**，
说明这是对**已存在的祷告室**的重新设计。视觉部分改造量中等；但设计稿里
「16 人在线」「❤️ 12」「5 分钟前」这些**真实感很强的元素，背后的数据和实时能力目前一样都没有**。

如果只做视觉，两三天能出效果，但会变成一个**漂亮的假页面**——
在线成员是写死的，点赞数不会变，祷告分享刷新就没了。这与规范里
「不用空课程页伪装已可学习」是同一类问题，我不建议这样交付。

## 1. 现状审计

### 1.1 祷告室已经存在

`components/VoiceRoom/` 是一个 **2212 行**的成熟模块，祷告室是其中 5 种房间类型之一：

| 房间 | key | 现有主题色 |
|---|---|---|
| **祷告室** | `prayer` | `text-rose-500` / `bg-rose-50`（浅玫瑰） |
| 赞美室 | `praise` | 浅琥珀 |
| 读经室 | `bible` | 浅蓝 |
| 讲道室 | `preaching` | 浅紫 |
| 交通室 | `fellowship` | 浅绿 |

五个房间**共用同一个 `VoiceRoomOverlay.tsx`（1591 行）**，靠 `THEME_CONFIGS` 切换文案与配色。

### 1.2 已经有的能力（可直接复用）

- **祷告墙**：房主可编辑的多行文本，对应设计稿的「本次祷告主题」——概念已存在
- **参与者模型**：`Participant` 含 `role: host | admin | speaker | listener | member`、
  `isSpeaking`、`degree`、`isMutedByHost`；房主/管理员权限判断齐全
- **语音传输层**：`services/voiceTransport/` 已抽象为 `mock | livekit | agora` 三种实现，工厂切换
- **房间密码**：后端 `rooms` 表有 `password_hash` + `salt`，进房校验已实现
- **礼物 / 回应 / 邀请 / 分享录音**：都已存在
- **底部输入框**：`chatInput` + 发送逻辑已有（设计稿底部输入区可复用）

### 1.3 缺的能力（这才是真正的工作量）

| 设计稿元素 | 现状 | 缺什么 |
|---|---|---|
| 「16 人在线」+ 6 个头像 | **只有「我」一个人，硬编码** | 真实成员列表 + 在线状态 |
| 皇冠标记房主（以诺 👑） | role 模型有，UI 没有 | 仅 UI |
| 「本次祷告主题」4 条编号列表 | 祷告墙是**纯文本 + localStorage** | 结构化条目 + 后端表 + 多人同步 |
| 「祷告分享」feed | **完全没有** | 数据表 + API + UI |
| 「❤️ 12」点赞数 | **完全没有** | 表 + API + 实时更新 |
| 「5 分钟前」相对时间 | 无 | 小工具函数（简单） |
| 三个功能入口卡 | **没有**（经文默想、安静等候是新概念） | 需求定义 + 实现 |
| 深色暗金主题 | 现在是**浅色** | 见 §3 决策 A |

### 1.4 两个结构性缺口

**① 没有房间级实时通道。**
后端确实有 WebSocket（`backend/src/server.ts:86`），但它**只是 Gemini Live 的代理**，
不是房间广播。所以目前做不到：谁进来了、谁离开了、谁刚发了祷告、点赞数变了。

**② 祷告数据全部是单机的。**
祷告墙存在 `localStorage['amas_prayer_wall_<roomId>']`——
房主编辑的祷告主题，**其他人根本看不到**。后端 `rooms` 表只有 5 个字段：
`room_id / host_id / password_hash / salt / created_at`，没有任何祷告内容。

## 3. 需要你拍板的决策

### 决策 A：深色主题的适用范围 ⚠️ 最重要

设计稿是**深色暗金**，现有五个房间是**统一浅色**。三个选项：

| 方案 | 说明 | 代价 |
|---|---|---|
| **A1 只有祷告室深色**（推荐） | 祷告室独立主题，其余四间不动 | 需要把 `THEME_CONFIGS` 扩出主题层；两套配色并存，后续维护要注意 |
| A2 五个房间全部深色 | 视觉最统一，气质最好 | 要重做 1591 行里所有硬编码的浅色类名，回归测试范围大 |
| A3 全 App 深色 | — | **不建议**，远超本次范围，且与规范「不重新推翻当前整体视觉风格」冲突 |

我倾向 **A1**：祷告本身就适合暗色沉静的氛围，与赞美室的明亮形成对比是合理的设计语言，
而且改动可控。但如果你想要五间统一，需要把工期按 A2 算。

### 决策 B：「❤️ 点赞」的语义 ⚠️ 建议改

设计稿在祷告分享上放了「❤️ 12」。但内容是：

> Mary：求主医治我母亲的身体，赐下平安与力量。

**给这样的内容「点赞」在语义上是别扭的**——没有人是在「赞」一位母亲生病。
建议把它改成**代祷计数**：

- 图标：🙏 或蜡烛，不用 ❤️
- 文案：**「我为你祷告」**，计数显示「12 人正在为此祷告」
- 点了之后可以（可选）进入自己的代祷清单

这比点赞更贴合场景，也更有牧养价值。**数据结构完全一样，只是语义和文案不同**，
现在定下来成本为零，上线后再改就要迁移数据。

### 决策 C：三个入口卡到底是什么

设计稿写了「祷告事项 / 经文默想 / 安静等候」，但只有副标题，没有交互定义：

- **祷告事项**：是 §2 的祷告主题的详情页？还是每个人可以提交自己的代祷事项？（两者差别很大）
- **经文默想**：「每日一节经文」——从哪来？固定经文表 / 后端配置 / 复用读经室数据？
- **安静等候**：「安静在主里等候祂」——是计时器？背景音？纯静默页面？

这三个我需要你给一句话说明各自点进去发生什么，否则我只能凭猜，做出来大概率不是你想的。

### 决策 D：实时性做到哪一档

| 档位 | 做法 | 效果 | 成本 |
|---|---|---|---|
| **D1 轮询**（推荐先做） | 每 10~15 秒拉一次 | 在线人数、新祷告、代祷数会更新，略有延迟 | 小，无需新架构 |
| D2 SSE 单向推送 | 服务端推 | 近实时，实现比 WS 简单 | 中 |
| D3 WebSocket 房间广播 | 双向 | 真正实时，为将来"谁在说话"打基础 | 大，要改服务器架构 |

建议 **先 D1 上线，架构上预留 D3**。祷告室不是抢红包，10 秒延迟完全可接受。

### 决策 E：祷告分享的隐私边界 ⚠️

「求主医治我母亲的身体」属于**敏感个人信息**，涉及第三方（母亲）。必须先定：

- 谁能看见？（仅房内 / 全体学员 / 可选匿名）
- 保留多久？（祷告会结束即焚 / 保留 7 天 / 永久）
- 能否删除、能否举报？
- 是否允许匿名发布？

**我的建议**：默认**仅房内可见**、**支持匿名**、**发布者可随时删除**、
默认保留 30 天后自动归档。这条不定清楚，我不建议上线这个模块。

## 4. 数据模型（初稿，待决策后定稿）

```sql
-- 房间祷告主题（取代 localStorage 祷告墙）
CREATE TABLE room_prayer_topics (
  id TEXT PRIMARY KEY,
  room_id TEXT NOT NULL,
  seq INTEGER NOT NULL,          -- 显示序号 1/2/3/4
  text TEXT NOT NULL,
  created_by TEXT NOT NULL,
  created_at INTEGER NOT NULL
);

-- 祷告分享
CREATE TABLE prayer_shares (
  id TEXT PRIMARY KEY,
  room_id TEXT NOT NULL,
  user_id TEXT NOT NULL,
  text TEXT NOT NULL,
  is_anonymous INTEGER NOT NULL DEFAULT 0,
  created_at INTEGER NOT NULL,
  deleted_at INTEGER                -- 软删除，发布者可撤回
);

-- 代祷计数（决策 B：不是点赞）
CREATE TABLE prayer_intercessions (
  share_id TEXT NOT NULL,
  user_id  TEXT NOT NULL,
  created_at INTEGER NOT NULL,
  PRIMARY KEY (share_id, user_id)   -- 一人一次，可取消
);

-- 在线成员（决策 D1：心跳 + 超时判离线）
CREATE TABLE room_presence (
  room_id TEXT NOT NULL,
  user_id TEXT NOT NULL,
  role TEXT NOT NULL,
  last_seen_at INTEGER NOT NULL,
  PRIMARY KEY (room_id, user_id)
);
```

配套 API：`GET/POST /api/rooms/:id/topics`、`GET/POST/DELETE /api/rooms/:id/shares`、
`POST/DELETE /api/rooms/:id/shares/:sid/intercede`、`POST /api/rooms/:id/heartbeat`。

## 8. 实施记录（开发后补充）

### 8.1 一处实测修正：房间内部本来就是深色

原分析 §3 决策 A 说「现有五个房间是统一浅色」，**这条不准确**。
`THEME_CONFIGS` 里的 `bg-rose-50 / text-rose-500` 只用在**房间列表卡片**上；
房间打开后的 `VoiceRoomOverlay` 一直是深色（`bg-[#3b0b1a]`、`bg-[#12121e]`、`text-white`）。
因此 A1 的成本比原估算低——不需要重做配色体系，只需要重做**版式**。

### 8.2 已交付

| 项 | 实现 |
|---|---|
| 数据表 | `room_prayer_topics` / `prayer_shares` / `prayer_intercessions` / `room_presence` |
| 后端 | `backend/src/routes/prayer.ts`，8 个接口，全部 `requireAuth` |
| 前端数据层 | `services/prayerRoomService.ts`，10 秒轮询 + 20 秒心跳 |
| 面板 | `components/VoiceRoom/PrayerRoomPanel.tsx`，只在 `prayer` 房间生效 |
| 接入 | `VoiceRoomOverlay` 把 `isPrayerRoom` 分支切给新面板，其余四间原样不动 |

**单接口设计**：`GET /api/rooms/:id/prayer` 一次返回 主题 + 在线成员 + 分享 + 我的代祷 + 服务器时间，
轮询只打一个请求。相对时间以 `serverTime` 为基准，避免客户端时钟偏差算出「-3 分钟前」。

### 8.3 决策的落地方式

- **B**：接口叫 `intercede` 而非 `like`，按钮是 🙏「我为你祷告」/「N 人正在为此祷告」，无 ❤️、无点赞语义。
- **E**：`prayer_shares` 有 `is_anonymous` 与 `deleted_at`（软删除）；匿名分享**后端不向任何人返回 `user_id`**，
  发布者本人靠 `isMine` 判断删除权；删除权限 = 发布者本人 或 房主。
- **D1**：`PRESENCE_TTL_MS = 45s`，超时即视为离线；离开房间时 `DELETE presence`。

### 8.4 §3 决策 C 仍未定义，当前用的是最小可辩护实现

三个入口卡已按设计稿渲染，行为是我暂定的，**等你确认后再调整**：

| 卡 | 当前行为 | 依据 |
|---|---|---|
| 祷告事项 | 滚动定位到「本次祷告主题」 | 卡片副标题写的是「查看并参与代祷事项」 |
| 经文默想 | 每日一节经文详情页，按日期确定性选取，全房同一节 | 副标题「每日一节经文」 |
| 安静等候 | 静默页 + 计时器 + 呼吸动效，无声音 | 副标题「安静在主里等候祂」 |

经文取自内置 7 节祷告主题经文轮换。**如果你要的是别的，改动很小。**
